## Сводка куратору о паре: присутствующие + отсутствующие (`bb26421`)

Запрос владельца: «надо чтоб куратор знал об отсутствующих. даже если оценок
не было, куратору всё равно надо отправить информацию по присутствующим
и отсутствующим».

### Что было не так

Сообщение куратору (api.py, `/conduct`) собиралось из `changed` — списка
**изменённых** оценок. Отсюда два дефекта:
1. «Ниже список отсутствующих:» печаталось, но список всегда был пуст
   (в коде стоял комментарий «оставляем пустым списком»).
2. При `notified == 0` был ранний `return` — если оценки не ставили,
   а только отмечали посещаемость, куратор не получал ничего.

### Как сделано

- `_student_fio(row)` — «Фамилия И.», как в остальных пушах.
- `_curator_conduct_text(db, lesson_id)` — строит сводку по **всему составу
  группы** (`db.get_group_students`), а не по изменённым:
  - присутствие = строка в `grades` (`'0'` печатается прочерком «—»);
  - отсутствие = нет строки или `'absent'`;
  - если отсутствующих нет — строка «нет».
- Убран ранний выход при `notified == 0`; проверка активности бота осталась.
- Текст собирается **в контексте запроса**, в поток уходит готовая строка
  (раньше поток обращался к БД после закрытия контекста).
- `fio_map` удалён — больше не нужен.

Студентам по-прежнему уходят только изменённые оценки (`notify_grade`).

## Цветовые маркеры в сводке куратору (`f49cf1a`)

Запрос: «можно изменять цвет букв, серым которые не получили оценку,
оценённые пусть будут зеленые, и красным пропустившие».

**Цвет текста MAX не поддерживает.** Проверено по официальной схеме
`max-messenger/api-schema` (`schema.yaml`, раздел «Text formatting»):
- HTML: только `<i>/<em>`, `<b>/<strong>`, `<del>/<s>`, `<ins>/<u>`, `<a>`,
  `<pre>/<code>`, `<mark>`, `<blockquote>`, `<h1>`. Ни `<font>`, ни
  `<span style>` — всё остальное клиент вырезает;
- markdown: `*курсив*`, `**жирный**`, `~~зачёркнутый~~`, `++подчёркнутый++`,
  `^^красная подсветка^^` (единственный реальный цвет — красный фон),
  `` `код` ``, `> цитата`, `# заголовок`.

Решение: цветные кружки-эмодзи. Константы в `api.py`:
`_MARK_GRADED = '🟢'`, `_MARK_NOGRADE = '⚪'`, `_MARK_ABSENT = '🔴'`.

Пример (реальный урок 31, ИТС-31):
```
Список студентов и через дефис оценка
🟢 Гаус Э. - 5
🟢 Рыцарев С. - 4
Ниже список отсутствующих:
🔴 Энгель К.
```
Студент с '0' печатается как `⚪ Иванов И. - —`.

Тесты обновлены на маркеры; 524 passed.

## Найдена причина красного Test stand (`25b8907`)

Владелец прислал лог шага «Run stand» (и распакованный отчёт Playwright —
он же лежит в `%TEMP%\Rar$EXa*.rartemp\playwright-report\index.html`,
внутри `report.json` с `errors: ["Error: Process from config.webServer
was not able to start. Exit code: 1"]`).

**Причина:** консоль Windows-раннера по умолчанию **cp1252**, а
`stand_seed.py` печатает русский текст (`Сид готов: …`). Скрипт падал с
`UnicodeEncodeError` → возвращал ненулевой код → `e2e_server.py` пытался
залогировать это тем же русским текстом (`— сидируем сами`) → падал сам
→ Playwright не мог поднять webServer.

Фазы static, backend и api проходили; красной была только e2e.
Поэтому стенд не был зелёным ни разу с 13.10 — не регрессия от правок.

**Исправлено:**
- `stand_seed.py` и `mobile-teacher-app-redesign/e2e_server.py` —
  `stream.reconfigure(encoding='utf-8', errors='replace')` для stdout/stderr
  (та же защита, что с самого начала есть в `stand.py`, строки 44-47);
- `log()` в `e2e_server.py` при `UnicodeEncodeError` печатает ASCII-безопасно;
- `.github/workflows/test-stand.yml`: шагу Run stand добавлен
  `PYTHONIOENCODING: utf-8`.

**Проверка локально под cp1252** (точное условие раннера):
`stand_seed.py` — exit 0 с русским выводом; `e2e_server.py` — отвечает 200;
`npx playwright test` — 6 passed.

**Вывод на будущее:** любой скрипт, который печатает кириллицу и запускается
в CI на Windows, обязан либо ставить reconfigure, либо получать
`PYTHONIOENCODING=utf-8`.

## Группа под номером пары была невидимой (`367f38f`)

Владелец: «в расписании и везде где указывается номер пары, название группы
надо писать под парой».

Подпись там **уже была**, но её не было видно: `PairNumber.code` красился
`colorForGroup(name).fg`, а `fg` в `lib/groupColors.ts` — это цвет текста
**поверх цветной плитки**, подобранный по WCAG к `bg`. У тёмных тонов
(4 курс, `l=42`) он белый → на белой карточке текст исчезал.
Проверка: `getComputedStyle` дал `rgb(255,255,255)`.

Исправлено:
- `groupColors.ts`: вычисление hue вынесено в `hueFor()`; добавлен
  `groupInk(name)` — тот же hue, но тон, читаемый на нейтральном фоне
  (светлая тема: `l = 40 − (курс−1)*5`, не ниже 24; тёмная: `l = 56 + (курс−1)*6`,
  не выше 80). Курс по-прежнему различается тоном.
- `Schedule.tsx`, `Today.tsx`: `codeColor = groupInk(group.name)`.
- Дубль группы в строке под предметом убран (`meta` = только время/комната;
  в «Сегодня» — время и средний балл).

**Правило на будущее:** `colorForGroup().fg` — только для текста на `bg`
(чипы, плитки). Для текста на карточке/странице — `groupInk()`.

Проверено: 14.10, пять пар — подписи видны у всех; «Сегодня» — тоже.

## График аналитики: порядок по датам (`c3e2ebb`)

Причина неправильной оси X: ряд строился обходом `db.lessons`, а этот массив
приходит сгруппированным **по предметам** (из gradebook'ов), не по датам.
Поэтому точки шли 30.09 → 26.09 → 15.10, и `last3` для дельты брались
не последние по времени.

Исправление в `Analytics.tsx`: `heldLessons` сортируется по `date`
(ISO-строки — лексикографически), тай-брейк по `id` внутри одного дня.
`.filter()` возвращает новый массив, поэтому `db.lessons` не мутируется.

Проверено: подписи оси 03.09 → 16.09 → 15.10. Playwright 6 passed.

**Осталось на усмотрение владельца:** на графике по-прежнему одна точка
на занятие, поэтому при трёх группах в один день линия пилообразная.
Если нужен сглаженный тренд — агрегировать по дате (среднее за день).
